## Назначение проекта

**MapControl** — локальный инструмент для **безопасного добавления новых объектов** на карту выполненных работ сайта [zavodsvay.ru](https://zavodsvay.ru/).

Краткая формулировка:

> Оператор собирает данные и фото объекта, LLM приводит текст к деловому и единообразному виду, определяет категорию объекта и считает количество свай из описания. Заявка сохраняется локально, дублируется на email администратора, после чего администратор модерирует заявку, кадрирует изображения и публикует объект в пайплайн сайта.

**MapControl не является SSOT.** После публикации источником правды остаётся `data/map.json` в `Zavodsvay-Static`.

## Текущее состояние

На конец сессии реализован **рабочий MVP операторского контура**:

- создание черновика заявки
- редактирование заголовка, описания и координат
- выбор точки на **Яндекс.Картах v3** или ручной ввод
- загрузка фото и конвертация в **WebP** через `sharp`
- проверка текста через LLM
- **LLM определяет категорию объекта** (`category_suggested`) из 9 значений
- **LLM считает количество свай** (`pileCount_suggested`) если число явно указано в тексте
- применение предложенного текста или сохранение исходного варианта оператора
- оператор может скорректировать `category` и `pileCount` вручную после LLM-заполнения
- отправка заявки в `data/submissions/pending/`
- **SMTP-отправка заявки на email администратора** вместе с JSON и изображениями (настраиваемый SMTP: Gmail / zavodsvay.ru / Yandex / mail.ru)
- базовая защита backend: `sanitizeId`, защита от path traversal, валидация входов
- исправление зависания UI при ошибке LLM
- применена тема **Sky Pro**: новый дизайн фронта (см. раздел ниже)
- **скрытый запуск** через `start.vbs` → `launcher.js`: авто-порт, ожидание готовности сервера, открытие браузера
- **корректный выход**: кнопка «✕ Выход» → диалог → POST `/api/shutdown` → UI меняется на «Сервер остановлен / Закрыть окно» (без зависания браузера)
- **ярлыки на рабочем столе**: `scripts/create-shortcuts.vbs` генерирует `MapControl.lnk` и `Update MapControl.lnk`
- **скрытое обновление**: `update.vbs` запускает `update.bat` без консольного окна; `update.bat` проверяет, что сервер закрыт
- **localhost вместо 127.0.0.1**: `launcher.js` использует `localhost` для совместимости с ключом Яндекс.Карт
- **GPS из EXIF**: координаты извлекаются из метаданных первого загруженного фото (пакет `exifr`), автоматически заполняют поля lat/lng
- **Вставка координат одной строкой**: поле широты принимает вставку «55.915, 57.870» и разбирает в lat + lng
- **Фикс вложений письма**: отправка и submit копируют только фото из meta.images, а не все файлы из папки (защита от накопившихся orphan-файлов)
- **Локальные шрифты Inter**: woff2-файлы (latin + cyrillic, 400/500/600/700) в `public/fonts/`, без внешних CDN-зависимостей
- **Переключение темы**: кнопка ☽/☀ в шапке, выбор сохраняется в localStorage, `[data-theme="dark"]` в CSS
- **Блок-схема приложения**: `MapControl.bpmn` в корне (процессы запуска и заявки, дорожки оператора и сервера)

### Ключевые решения (обновлено)

#### Фильтрация вложений письма (2026-07-04)

Ранее `sendSubmissionEmail` читала все файлы из `pending.images/` через `fsp.readdir`, а submit копировал все файлы из `draft.images/`. Оператор в течение дня мог загрузить десяток фото в один черновик (разные объекты, исправления), и при отправке все они уходили в письме.

Исправлено: и копирование при submit, и вложения письма фильтруются строго по `meta.images[]`. Только фото, перечисленные в метаданных заявки, попадают в pending и в письмо.

#### GPS из EXIF фото (2026-07-04)

Пакет `exifr` парсит GPSLatitude/GPSLongitude из сырого буфера загрузки до обработки sharp. Координаты возвращаются в ответе `POST /api/.../images` как поле `gps: { lat, lng }`. Фронтенд заполняет поля lat/lng, если они ещё пусты.

#### Вставка координат одной строкой (2026-07-04)

Поле широты обрабатывает событие `paste`: если в буфере обмена строка с двумя числами (разделители: запятая, точка с запятой, пробел), они автоматически разносятся в lat и lng. Определение порядка: если первое число > 90, оно считается долготой.

#### Локальные шрифты Inter (2026-07-04)

Шрифт Inter (latin + cyrillic, начертания 400/500/600/700) зашит в `public/fonts/` как woff2-файлы из пакета `@fontsource/inter`. `@font-face` объявления с `unicode-range` подключают латиницу и кириллицу раздельно — браузер загружает только нужный файл. Внешняя зависимость от Google Fonts CDN убрана.

#### Переключение светлой/тёмной темы (2026-07-04)

Кнопка ☽/☀ в шапке переключает `data-theme="dark"` на `<html>`. Выбор сохраняется в `localStorage` (ключ `mapcontrol-theme`). Тёмная палитра задана через CSS-переменные в `[data-theme="dark"]` и дополнительные правила для компонентов, не использующих переменные.

## Ключевое решение по LLM

### Что проверяли

Тестировалась связка **Qwen 3.5 Flash** через OpenAI-compatible провайдеров.

Изначально использовался `vsellm.ru` с моделью:

```text
qwen/qwen3.5-flash
```

Проблема оказалась не в качестве модели, а в том, что провайдер по умолчанию запускал reasoning/thinking, из-за чего:

- output раздувался до ~2.3K токенов
- запрос шёл до 1.5–2 минут
- UI сценарий оператора становился непригодным

### Что не сработало

Эти способы у `vsellm` не решили задачу полностью:

- `thinking: { type: 'disabled' }`
- `/no_think` в prompt

### Что сработало технически

Для Qwen на vLLM-совместимом провайдере сработал параметр:

```json
{
  "chat_template_kwargs": {
    "enable_thinking": false
  }
}
```

После этого на `vsellm` usage стало нормальным — примерно **332 → 96** токенов, то есть thinking действительно отключался.

### Почему `vsellm` всё равно не подошёл

Несмотря на технически правильное отключение thinking, latency остался слишком большим — около **90 секунд**. Для операторского интерфейса это неприемлемо.

### Текущее рабочее решение

Выбран провайдер **RouterAI**:

```env
LLM_BASE_URL=https://routerai.ru/api/v1
LLM_MODEL=qwen/qwen3.5-flash-02-23
```

Практический результат на тесте:

- input/output порядка `331 / 138`
- latency около **1.9 сек**
- цена запроса около **0.0053 ₽**
- ответ оборван (исходный текст утерян)
